# تشغيل Gate 34 إلى Gate 38 يدويًا

## قبل البدء

1. تأكد أنك داخل مشروع Supabase الصحيح الخاص بـ ONEXA.
2. خذ نسخة احتياطية أو Export حديثًا قبل أي تعديل.
3. افتح **SQL Editor** وأنشئ Query جديدة لكل ملف؛ لا تجمع الملفات كلها في تشغيل واحد.
4. اترك مفاتيح التشغيل `VITE_ENABLE_ONEXA_POSTING` و`VITE_ENABLE_ONEXA_SALES_POSTING` مغلقة.
5. اترك `VITE_ENABLE_ONEXA_PROCUREMENT_POSTING` مغلقًا حتى اكتمال فحص Gate 36.
6. اترك `VITE_ENABLE_ONEXA_PAYROLL_POSTING` و`VITE_ENABLE_ONEXA_ASSET_POSTING` مغلقين حتى نجاح فحوص Gate 37 وGate 38.

## الترتيب الإلزامي

يجب أن تكون الجداول الأساسية الثلاثة `ready`، ويجب أن يظهر فحص `onexa_post_journal` بحالة `ready`. يجب أيضًا أن تكون كل الأعمدة المطلوبة `ready`.

إذا ظهر `signature_mismatch_or_missing` أو أي `missing`، توقف ولا تنفذ الملفات التالية. انسخ كامل النتائج لإعادة تكييف الحزمة مع مخطط الإنتاج الفعلي.

## ما ترسله بعد التنفيذ

أرسل نتيجة ملف `00` أولًا. وبعد نجاح Gate 34 وGate 35 أرسل نتائج ملف `03`، خصوصًا:

1. توقيع `onexa_post_journal`.
2. جدول حالة الكائنات وRLS.
3. صلاحيات الدوال.
4. قائمة `onexa_sales_posting_configuration_gaps`.

بعدها يتم تجهيز كود ربط أرقام الحسابات الحقيقية، ثم B3، ثم اختبار فاتورة بيع تجريبية وترحيلها وعكسها.

4. أعد `gate39_postcheck.sql` وتأكد من خلو فجوات الحسابات وعدم وجود أرصدة سالبة.

## Gate 58 — القيود اليومية اليدوية وتصحيح القيود المرفوضة

**الحالة الحالية: التطوير البرمجي والاختبارات المعزولة فقط. لا تُفعّل على الإنتاج.**

**عائق محاسبي مؤكد بتاريخ 18-11-2026:** قيد `onexa_journal_headers_source_document_type_check` المثبت حاليًا لا يسمح بالمصدر `manual_journal`، وشرط توازن رأس الأستاذ `onexa_journal_headers_check` ومحرك B4 يسمحان بفارق `0.005`. نجاح Gate58 وحده لا يكفي؛ تحقق من الملف `gate58_b4_live_contract_readonly.sql` (قراءة فقط)، ولا تستخدم أي حزم `REVIEW_ONLY` إلا في Staging مستقلة بعد استعادة مثبتة وموافقة مالية وأمنية. انظر `docs/runbooks/onexa-b4-shared-ledger-integrity-2026-11-18.md`.


توفر حزمة المصدر دورة محكومة: إنشاء المسودة، إرسالها، مراجعتها واعتمادها بواسطة مستخدم مختلف، ترحيلها إلى الأستاذ، ثم عكسها. كما تدعم تعديل المسودات والقيود المرفوضة فقط عبر `onexa_amend_manual_journal`، حيث يحتفظ القيد برقمه، ويزيد رقم المراجعة، ويحفظ تفاصيل ما قبل التصحيح وبعده في سجل الأحداث.

- لا يسمح بتعديل القيود المرسلة أو المعتمدة أو المرحلة أو الملغاة أو المعكوسة.
- رفض القيد يتطلب صلاحية الاعتماد، ولا يجوز لمنشئه رفضه بنفسه.
- بعد رفض القيد، لا يمكن إعادته لمسودة عبر تبديل الحالة فقط: يلزم حفظ تصحيح محكوم، ثم إرساله من جديد.
- هوية القيد المحاسبية (الكيان والفرع والتاريخ والفترة والعملة) ثابتة عند التصحيح؛ تغييرها يستلزم إنشاء قيد جديد.
- تحفظ الأبعاد المحاسبية مثل المشروع ومركز التكلفة أثناء تصحيح السطور، ويُراجع سجل نسخ السطور.
- يمنع تحديث قيد تغير رقم مراجعته منذ فتح الشاشة. وتُرفض الفروق النقدية غير المتوازنة وأجزاء الهللة في الريال السعودي.
- حفظ التصحيح وإرسال القيد عمليتان منفصلتان؛ عند فشل الإرسال تبقى المسودة موجودة ويمكن إعادة إرسالها دون إنشاء نسخة أخرى.

1. أنشئ بيئة **ONEXA Staging مستقلة بالفعل**، بقاعدة بيانات وبيانات اختبار وهمية ومستخدمين مخولين مستقلين عن الإنتاج.
