# Gate 73 — Native work-order lifecycle acceptance

**Current state: SQL SOURCE ONLY. Not applied or tested against customer production.** Requires the approved, staged, successfully tested ONEXA Gate 71 company aliases and Gate 72 native operation sites/assets. Never deploy legacy global `ops_work_orders` on a multi-tenant ONEXA data plane.

## Database boundary and business flow

`onexa_operations_work_orders` is a new tenant-native work-order table. Every order stores the ONEXA tenant, legal entity, branch, site, optional asset, active customer and optional active contract. It uses composite foreign keys enforcing `(tenant_id, legal_entity_id, branch_id, site_id)` on the site, the same four values plus `asset_id` on the asset, `(tenant_id, customer_id)` on the customer, and `(tenant_id, contract_id, customer_id)` on the contract. Cross-tenant records and contracts linked to another customer cannot be inserted even through privileged provisioning. Gate 73 adds supporting unique composite indexes to the existing `customers`, `contracts` and Gate72 asset registry; verify production index-build impact before DDL.

`onexa_create_operations_work_order` requires active tenant claim/workspace membership, `projects.create`, authorized active `OM → projects` company alias, an active site/branch/entity, an active customer, an optional active asset in **that same site**, and an optional active contract for **that customer** covering today's date. It writes one draft and one append-only creation event. Numbers are generated by a database sequence, never by client input.

`onexa_transition_operations_work_order` locks the order row before changes and atomically appends the transition event. Allowed statuses:

| From | To | Actor rule |
|---|---|---|
| draft | approved | `projects.approve`; creator cannot approve |
| draft / approved / assigned | cancelled | `projects.approve` |
| approved | assigned | `projects.approve` and active assignee in same tenant |
| assigned | in_progress | assigned active member or manager |
| in_progress | on_hold / completed | assigned active member or manager |
| on_hold | in_progress | assigned active member or manager |
| completed | accepted | `projects.approve`; acceptor cannot be creator or completer |
| accepted / cancelled | no transitions | terminal immutable |

All transitions require a nonempty reason. Completing stores the responsible actor, completion date and completion note. Approvals, assignments and acceptance are auditable. Original tenant/customer/site identity cannot be reassigned, even in draft. Direct authenticated table mutation is denied. Database triggers require the workflow's transaction context for all updates/events; the event journal cannot be edited or deleted by a service role. Privileged service identities must still be controlled by operations security procedures.

Tenant-scope RLS is enforced in `onexa_operations_work_orders` and its events table; only active workspace members with `projects.read`, plus an authorized active OM legal-entity/branch/site scope, can see orders. This does **not** implement narrower within-tenant per-branch assignee-only restrictions; these require separately authorized branch-access policies if desired.

## Dashboard behavior (feature-flag OFF by default)

The existing maintenance route is wrapped by `ModuleAccessGuard` **before** its data-query component mounts. On an ONEXA tenant, legacy `ops_*` requests are never made. Until Gate71/72/73 are fully accepted and both `VITE_ENABLE_ONEXA_TENANT_COMPANY_SCOPES` and `VITE_ENABLE_ONEXA_NATIVE_WORK_ORDERS` are explicitly enabled, the new dashboard stays read-disabled and presents a not-activated notice rather than a fake empty deployment. When enabled, it reads native work orders and assets under server-side RLS, and the legacy Gate66 cost widget is hidden. The original legacy-mode dashboard remains available only on a separately authorized non-tenant legacy installation.

This read-only native dashboard is a first step: create, assign, approve and complete **buttons** are not enabled in the UI until staged tests establish the RPC contract and specific user roles. The backend workflow SQL is not production-ready solely because the UI displays it.

## Explicit scope exclusion

There is **no GL journal**, cost recognition, inventory issue, payroll, approval workflow engine (G62–64), service-level agreement timer, push-notification trigger, full technician availability engine, or work-order UI in Gate 73. In particular, Gate66's existing legacy `ops_work_orders` cost bridge is **not** compatible with native `onexa_operations_work_orders`; it must be redesigned and approved as a separate accounting gate. No automatic migration/copy from the old legacy work-order schema is safe.

## Deployment and security acceptance

1. Confirm correct customer instance, reviewed schema, tested backup/restore and approved change window.
2. On an isolated **disposable staging clone**, apply Gate71 and Gate72 in order, with postchecks and approved scope/branch test fixtures. Confirm Gate72's corrected PL/pgSQL trigger delimiters (PR #63).
3. Verify no Gate73 objects exist; inspect `customers`, `contracts`, `onexa_operations_assets` for unique index conflicts and downtime/locks. Apply `gate73_onexa_native_operations_work_orders.sql` only to the approved staging clone.
4. Execute `gate73_postcheck.sql` and require READY on all objects, four validated order composite FKs, the event tenant FK, active RLS/immutability guards, and false anonymous permissions/client DML; anomaly queries return zero.
5. Create **two independent staging tenants** with legal entities, branches, approved OM scopes, sites, assets, customers and active contracts. With tenant A credentials, attempt all RPCs using a known tenant B site, asset, customer, contract, assignee and work order ID. All must reject or return no rows. Repeat with tenant B.
6. Test mismatch asset vs same-tenant wrong site, mismatch contract vs customer, inactive entity/branch/scope/site/customer/asset/contract, expired contract, missing permission, invalid transition, duplicate completion/acceptance, actor separation, concurrency and role downgrade mid-process.
7. Verify all allowed transitions and event ordering with authorized independent actors, including completion note and terminal immutability. Attempt direct INSERT/UPDATE/DELETE as authenticated and reject; attempt privileged identity rewrite/event deletion and reject. Confirm failed actions rollback without extra events.
8. Re-run negative tests after new tenant/company onboarding and before any live work orders are created. Only then consider approved production DDL and deployment. Keep all maintenance-cost/accounting flags off.

**Stop conditions:** missing G71/G72, unavailable backup/clone, SQL execution failure, incomplete composite FK, RLS bypass, cross-tenant access, unapproved manager/creator separation, unlogged status change, any unexpected ledger posting, or an incompatible cost bridge.

**GitHub CI is source validation only**, not evidence of SQL installation or two-tenant acceptance.
